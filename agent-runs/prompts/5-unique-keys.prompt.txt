================================================================================
THE TASK
================================================================================

A collection cannot say that a field is unique, and nothing creates an index.
Give `defineCrud` both.

    defineCrud('artifact', ArtifactSchema, { unique: ['digest'] })
    defineCrud('partVersion', PartVersionSchema, { unique: [['partName', 'version']] })

A single field, or a compound key. Optional; every existing caller keeps working.

================================================================================
WHY
================================================================================

`defineCrud` mints the document id, so a domain key — a content digest, a
hostname, a version — lives beside it as an ordinary field. Two rows can then
claim the same one, and nothing notices.

That is not theoretical in the consumer, `mesh-serve`:

  - `artifact.digest` is a sha256 of the bytes. **Content addressing exists
    precisely so two rows cannot claim the same content**, and today they can.
  - `site.host` is a hostname. Two rows, and which one a request gets depends on
    which the database returned first — so a tenant could take over a hostname by
    creating a second row for it.
  - `partVersion` is `(partName, version)`, and a *published version is
    immutable* is the property every version range depends on. It is enforced by
    a check-then-create in application code today, which is a race: two publishes
    of the same version can interleave between the check and the write.

The last one is the sharp case. The check is already written and correct, and it
cannot be made safe without the database refusing the second write — so this is
not "add a constraint", it is "make an existing guarantee true".

Search `mesh-serve/spec/building.md` §4a if you want the consumer's write-up.
You do not need that repository to do the work.

================================================================================
WHAT IT HAS TO GET RIGHT
================================================================================

1. **When is the index created?** At `defineCrud` time there is no database. At
   first `repo()` call there is, but that is a hot path. On `DatabaseModule`
   start there is a connection but the registry may not be populated yet. Pick
   one, say why, and make sure a second call does not pay for it again —
   `createIndex` is idempotent in mongo but a round trip per query is not free.

2. **A duplicate must fail legibly.** Mongo answers E11000 with a message naming
   an index, not a field. A caller seeing that has learned nothing. Turn it into
   a `MeshError` that names the collection, the field, and the value — the same
   standard as the `defineCrud` message that refuses an id field in a base
   schema, which teaches rather than merely refuses.

3. **Existing data.** A collection that already holds duplicates cannot take a
   unique index, and mongo will refuse to build one. Decide what happens: refuse
   to start, log and continue unindexed, or something else. **Failing to start is
   probably right and is not obviously right** — a node that will not boot because
   of old data is its own kind of outage. Say what you chose and why.

4. **Compound keys are ordered.** `['partName', 'version']` and
   `['version', 'partName']` are the same constraint and different indexes. Do
   not let a caller think the order is free, or normalise it and say so.

5. **`scopedBy` interacts with this.** A collection scoped by `tenantId` with a
   unique `slug` almost certainly means *unique within an organization*, not
   globally — two tenants both wanting the slug `main` is normal. Decide whether
   `unique` on a scoped collection includes the scope field automatically, and be
   careful: getting this wrong in the global direction breaks tenants for each
   other, and in the scoped direction lets two rows claim one hostname.

   `site.host` is the case that shows it is not simple: a site is scoped by
   tenant and its hostname must be **globally** unique, because a hostname is
   one origin on the internet.

HOW TO WORK
================================================================================

Investigate first. Read how `scopedBy` landed in v2.2.0 (`eb73ed1`) and match
its standard.

Point 5 is the one to think hardest about and the one most likely to need an
explicit per-collection answer rather than a rule. If you conclude the option
needs to distinguish "unique globally" from "unique within scope", say so and
design it — that is a better outcome than a default somebody has to remember.

A test for each decision above. `npm test` must stay green; there are 344 tests
on master.
