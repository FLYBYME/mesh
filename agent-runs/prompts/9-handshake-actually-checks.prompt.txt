--- 1. The shared key refuses nobody -----------------------------------------

A node was started with `MESH_KEY` set and port 4001 open. A process with **no
key at all** dialled it and joined:

    PEERS_SEEN=1 ["surf.surfdns.net"]
    READABLE user.find     -> []
    READABLE apiToken.find -> []

Those answered empty only because that database was empty. On a populated one it
is every user and every API token to anyone who can reach the port.

`WSTransport` sets `this.authKey = options.authKey ?? options.authToken ??
process.env.MESH_KEY`, so the value is **held**. Nothing checks it on an inbound
connection.

The key is presented **at the handshake** and checked **before the connection
becomes a peer**. A dialler that cannot present it must never reach
`registerNode`, PEX, or the broker — not "is refused when it calls something",
which is a different and much later thing.

**Three cases, all tested:**
  - correct key → connects, can call
  - wrong key → refused, and never appears in `registry.getNodes()`
  - **no key → refused**, same

A test that only asserts the happy path passes against the code as it stands
today. That is how this survived.

**Decide and state: what an unset `MESH_KEY` on the *listener* means.** It must
not mean "accept everybody" — that is the current behaviour and it is the bug.
I would make an unset key on a listener that is not loopback a **refusal to
start**, loudly, naming the variable: a node that cannot authenticate its peers
and is reachable from the internet should not run. Local development binds
loopback and is unaffected. Argue if you disagree, but pick something that fails
closed.

Say what a rejected dialler sees. A peer that silently fails to connect and a
peer with a wrong key must not look identical — that difference is the whole
diagnosis when six machines are involved.

--- 2. The bind host is ignored ----------------------------------------------

`new WSTransport(serializer, port, host)` takes a host. `bin/node.mjs` in
mesh-serve passes `127.0.0.1` by default. The socket binds `*:4001` regardless:

    ss -ltn  ->  *:4001

So there is no way to bind the mesh port to loopback, and the topology this whole
design rests on — **one machine with a public port, every other node on loopback
dialling out** — is not achievable from the runner. Every node that runs is
exposed.

Fix the binding. Add a test that a transport told `127.0.0.1` is not reachable on
another interface.
