--- 1. Shared-key authentication on the WS handshake (the hard one) --------

This is what stops seven machines becoming a fleet. mesh-serve delivered the
fleet layer and then deliberately refused to open a public port, because today
anything that reaches `ws://host:4001` becomes a peer and can call every tool on
the mesh.

Read `src/transports/node/WSTransport.ts` and `src/core/TransportManager.ts`
first. Note that WSTransport was just changed for ping/pong (dispatch 7,
merged) — you are working next to fresh code.

The key is presented **at the handshake** and checked **before the connection
becomes a peer**. A dialler that cannot present it must never reach
`registerNode`, PEX, or the broker. Authenticating the peer relationship is the
point; a per-call token is a different thing and not what is being asked for.

State in your plan, and again in the PR:
  - where the key comes from. **The environment, not a CLI flag** — a flag lands
    in `ps` output on a shared box.
  - what a rejected dialler sees. It must be diagnosable: a peer that silently
    fails to connect and a peer with a wrong key must not look identical.
  - whether unauthenticated loopback stays allowed. **I would keep loopback open
    and require the key whenever the listener is not loopback** — that makes the
    safe thing the default in the configuration people actually deploy, and keeps
    local development working. Argue if you disagree.

Test both directions: a correct key connects and can call; a wrong key and a
missing key are both refused and neither reaches the registry.

--- 3. A date does not survive a remote call --------------------------------

A remote CRUD `find` whose output contains a date fails **output** validation:

    ZodError: [ { "message": "Invalid date" } ]

Reproduce it before you fix it: join as a short-lived peer over `WSTransport`
and call `user.find` against a running node. The JSON serializer sends a `Date`
as an ISO string; the receiving side's schema still expects a `Date`, so a
correct response is rejected at the boundary. Local calls never see it, which is
why a full green suite has never caught it.

Every collection has `createdAt`/`updatedAt`, so this affects **every remote read
of every collection**.

**Serialization owns this, not each schema.** Do not fix it by loosening
contracts to accept strings — that spreads the problem across every schema in
every repository and makes the type lie about what the value is. Write the test
at the serializer boundary.
