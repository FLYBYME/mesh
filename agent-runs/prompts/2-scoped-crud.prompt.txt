================================================================================
THE TASK
================================================================================

Make a CRUD collection able to declare what scopes it, so a generated `find` is
always within the caller's resolved scope and an unscoped one is impossible to
write rather than merely discouraged.

    defineCrud('site', SiteSchema, { scopedBy: 'tenantId' })

`scopedBy` is optional. Every existing caller must keep working untouched.

================================================================================
WHY — READ THIS BEFORE YOU DESIGN ANYTHING
================================================================================

This is the single specific way a 100,000-line codebase went wrong, and the
sentence that names it is:

    Authorization can refuse a CALLER, but it cannot narrow a RESULT SET.

In that system `user.find` and `organization.get` were reachable as though
public, and a great many calls had no bounds. It is tempting to file that as an
authorization bug. It is not. An unbounded `find` has no notion of who is
asking, so `organization.find` returns every organization there is and *nothing
in the contract could have said otherwise*. The gate did its job. There was
simply nothing for it to narrow.

Today the plumbing for half of it exists and is not joined up:

  - the api resolves a caller's organization and puts it in `meta`
    (`meta.user.tenant_id`), and `DatabaseMiddleware` already passes `meta`
    through to hooks — see the comment at src/db/DatabaseMiddleware.ts:104
  - `defineCrud` has no idea any of that exists

So the missing join is exactly: "this collection is scoped by this field, and a
find is always within the caller's resolved scope."

Until it exists, "never expose an unbounded find" is a discipline. A discipline
is what the 100,000 lines had.

================================================================================
WHAT IT HAS TO GET RIGHT
================================================================================

These are the decisions. Do not skip them; they are the whole task.

1. EVERY read, not just `find`. `find_one`, `count`, `get` and `resolve` can
   all leak a row across a scope boundary. `get` is the sharp one: it takes an
   id, so scoping it means a row belonging to another scope must answer NOT
   FOUND — never "forbidden", because "it exists, but not for you" is itself a
   disclosure.

2. EVERY write. `update`, `replace` and `delete` take an id. Without scoping,
   a caller can modify a row they cannot read.

3. `create` sets the field rather than checking it. A caller who can name their
   own `tenantId` on create can write into somebody else's scope.

4. A caller with NO scope. Decide, and say which you chose and why: refuse the
   call, or return nothing? Refusing is louder and probably right. What must not
   happen is treating "no scope" as "no filter", which is how this fails open —
   and a thing that fails open under exactly the condition it exists for is
   worse than nothing, because it looks like it works.

5. An explicit query that names the scope field. If a caller passes
   `query: { tenantId: 'someone-else' }`, the caller's scope wins. Do not merge
   and hope. A test for this.

6. Internal callers. A service calling its own collection over the broker has no
   `meta.user`. Decide whether that is "unscoped and allowed" or "refused", and
   write the reasoning down — this is the decision most likely to be got wrong
   quietly, because getting it wrong in the permissive direction makes every
   test pass.

================================================================================
HOW TO WORK
================================================================================

Investigate first. Read both files and `DomainRepository.ts` before proposing
anything — a plan written from this prompt alone is a restatement of this prompt.

Then, before writing code, say:
  - what you found: the actual lines, the actual shape of the registry entry
  - what you will change, in files
  - your answers to decisions 4 and 6 above, with reasoning
  - anything in this prompt you think is WRONG. It was written from outside
    mesh, by someone reading it as a consumer. If the design does not fit the
    framework's grain, say so rather than forcing it.

Tests are the deliverable as much as the code. Each of the six points above is a
test whose absence is invisible: every one of them passes today by doing nothing.

`npm test` must stay green — 318 tests before you start. Do not change existing
behaviour for a collection that declares no `scopedBy`.

Do not add a Co-Authored-By trailer or any Claude/agent attribution to commits.
